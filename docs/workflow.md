# Workflow

Этот документ описывает базовую схему работы над проектом.

Файл сделан в универсальном виде, чтобы его можно было копировать в другие проекты без переписывания логики процесса.

## Базовая схема

Работа строится вокруг четырёх вещей:

- `commit`
- `CHANGELOG.md`
- `version`
- `git tag`

Схема простая:

1. Пользователь ставит задачу.
2. Codex делает изменения в проекте.
3. Пользователь проверяет результат.
4. Если результат подходит, пользователь пишет: `коммитим`.
5. Codex делает commit.
6. Так может повторяться много раз.
7. Когда пользователь считает, что накопилась версия, он просит собрать changelog.
8. Codex обновляет `CHANGELOG.md`, описывая изменения, накопленные с прошлого тега.
9. Пользователь решает, какой номер версии нужен.
10. Пользователь ставит git tag на последний commit этой версии.

## Что важно

- `CHANGELOG.md` не обязательно обновлять на каждом коммите.
- Обычно changelog собирается перед релизом или перед постановкой нового тега.
- В changelog пишутся не commit messages, а человеческое описание изменений на английском языке.
- `git tag` отражает версию релиза.
- Для версий используются annotated tags.
- tag обычно ставится на последний commit релизной пачки, где уже обновлён `CHANGELOG.md`.

## Язык файлов

По умолчанию в проекте рабочим языком считаем русский.

Это правило относится в первую очередь к:

- `README.md`
- `CHANGELOG.md`
- документам в `docs/`
- Git commit messages

Базовый стандарт такой:

- `README.md` ведётся на русском языке
- документы в `docs/` ведутся на русском языке
- `CHANGELOG.md` ведётся полностью на английском языке
- commit messages в Git пишутся на английском языке
- стандартные названия секций:
  - `Added`
  - `Changed`
  - `Fixed`

Важно: файл должен называться именно `CHANGELOG.md`.
Не нужно переводить имя файла, технические заголовки или описания изменений в changelog на русский язык.

Такой компромисс удобен для всех проектов:

- структура changelog остаётся привычной и совместимой с распространённой практикой
- записи changelog напрямую согласуются с английскими commit messages
- не возникает путаницы между проектами

Если для конкретного проекта заранее принято другое решение, например проект публичный и должен вестись на английском, это оговаривается отдельно.

Если отдельного решения нет, используется русский язык для `README.md` и документов в `docs/`, а английский язык для `CHANGELOG.md` и commit messages.

## Как заполняется CHANGELOG.md

В `CHANGELOG.md` используется стандартная схема:

- `Added`
- `Changed`
- `Fixed`

Принцип такой:

- `Added`
  Для новых возможностей, экранов, команд, режимов, файлов или крупных сущностей.

- `Changed`
  Для изменений существующего поведения, структуры, логики, интерфейса или процесса.

- `Fixed`
  Для исправлений ошибок, регрессий, поломок и некорректного поведения.

В changelog не нужно перечислять все коммиты подряд.
Нужно кратко и понятно описывать результат изменений для человека на английском языке.

Стартовый `CHANGELOG.md` хранится отдельным файлом в корне проекта.
Для новых проектов его нужно просто скопировать вместе с `docs/workflow.md`.
Дублировать полный шаблон changelog внутри этого документа не нужно.

## Совместный цикл работы

Этот раздел описывает практическую схему работы пользователя и Codex.

### Обычная работа

1. Пользователь ставит задачу обычным языком.
2. Codex изучает проект и делает изменения.
3. Пользователь проверяет результат в проекте.
4. Если результат подходит, пользователь пишет: `коммитим`.
5. Codex проверяет `git status`, добавляет нужные файлы и делает commit.
6. После commit работа продолжается дальше.

Commit message всегда пишется на английском языке.
Это правило действует даже если задача, README и docs ведутся на русском.

Примеры commit messages:

- `feat: add password length control`
- `fix: correct service preset selection`
- `docs: update workflow`
- `chore: update gitignore`

Такой цикл может повторяться много раз:

- сделали экран или страницу -> `коммитим`
- сделали форму -> `коммитим`
- поправили поведение -> `коммитим`
- обновили документацию -> `коммитим`

Во время обычной работы `CHANGELOG.md` не обновляется автоматически.
Он остаётся чистым до момента подготовки версии.

### Подготовка версии

Когда накопилось достаточно изменений и пользователь считает, что пора оформить версию, он пишет, например:

- `подготовь changelog для v0.1.0`
- `собери changelog с прошлого тега`
- `оформи это как версию v0.1.0`

После этого Codex:

1. Смотрит изменения с прошлого тега или с начала проекта, если тегов ещё не было.
2. Собирает не список коммитов, а понятное описание результата на английском языке.
3. Обновляет `CHANGELOG.md`.
4. Добавляет новый блок версии выше старых версий и ниже `Unreleased`.
5. Оставляет `Unreleased` сверху для будущих изменений.

После обновления `CHANGELOG.md` файл будет отображаться в `git status` как изменённый.
Это нормально: changelog тоже должен попасть в Git.

### Коммит changelog, annotated tag и push

После проверки changelog пользователь пишет:

- `коммитим changelog`

Codex делает отдельный commit только для подготовки changelog, например:

```bash
git add CHANGELOG.md
git commit -m "docs: update changelog for v0.1.0"
```

После этого пользователь вручную создаёт annotated tag на последний commit:

```bash
git tag -a v0.1.0 -m "Release v0.1.0"
```

Annotated tag отличается от обычного tag тем, что хранит отдельную запись Git:

- имя версии
- автора tag
- дату создания tag
- сообщение tag
- ссылку на commit

Для версий используем именно annotated tags, а не lightweight tags.

После создания annotated tag пользователь отправляет код и tag на удалённый репозиторий одной командой:

```bash
git push origin main --follow-tags
```

Эта команда отправляет:

- новые commit-ы ветки `main`
- annotated tags, которые относятся к отправляемым commit-ам

Важно: `--follow-tags` отправляет annotated tags.
Обычные lightweight tags, созданные командой `git tag v0.1.0`, эта команда не отправляет.

Итоговый ручной шаг релиза:

```bash
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin main --follow-tags
```

Tag лучше ставить после commit с обновлённым `CHANGELOG.md`.
Тогда tag указывает на состояние проекта, где версия уже описана в changelog.

## README.md

`README.md` в корне проекта должен создаваться и обновляться на основе шаблона:

- `docs/readme-template.md`

Правило работы такое:

- шаблон задаёт базовую структуру README
- базовую структуру без отдельной команды лучше не ломать
- при обновлении README нужно адаптировать только проектные части:
  - название проекта
  - краткое описание
  - статус
  - особенности структуры
  - проектно-специфичные документы

Если отдельного указания нет, Codex должен считать `docs/readme-template.md` основой для создания или обновления `README.md`.

## .gitignore

`.gitignore` в корне проекта должен создаваться и обновляться на основе шаблона:

- `docs/gitignore-template.md`

Правило работы такое:

- в репозиторий должны попадать исходники, документация, конфиги и lock-файлы
- в репозиторий не должны попадать зависимости, результаты сборки, логи, временные файлы, локальные `.env`, IDE-файлы и packaged-артефакты
- старый `.gitignore` нельзя удалять вслепую, если в нём есть проектно-специфичные правила
- непонятные и устаревшие строки нужно убирать или заменять понятными секциями

Если отдельного указания нет, Codex должен считать `docs/gitignore-template.md` основой для создания или обновления `.gitignore`.

## Типовые команды взаимодействия

Примеры фраз, которых достаточно в работе:

- `коммитим`
- `собери changelog`
- `подготовь changelog для тега v0.2.0`
- `оформи это как версию v0.2.0`

## Роли

### Пользователь

- ставит задачу
- проверяет результат
- решает, когда делать commit
- решает, когда накопилась версия
- решает, какой tag ставить

### Codex

- делает изменения в проекте
- делает commit по команде пользователя
- собирает changelog по команде пользователя
- оформляет блок версии в `CHANGELOG.md`
- не назначает версию самостоятельно без решения пользователя

## Минимальное правило

Если нет отдельной команды на обновление changelog, значит:

- работаем через обычные commit-ы
- `CHANGELOG.md` пока не трогаем
- changelog собирается позже, когда пользователь решит оформить версию
