# safe-file-writer

ESM-only пакет **durable-записи файлов на диск** с отложенным, разнесённым во времени
**бэкапом версий**. Задуман как единая точка, через которую проходит вся запись
приложения на диск.

- Платформа: **Node.js** (используются только `node:fs`, `node:path`, `node:crypto`).
- Package-зависимостей нет.

## Зачем пакет

Обычная «атомарная» запись `writeFile(tmp)` → `rename(tmp, target)` **без fsync** на NTFS
после жёсткого сбоя (потеря питания, BSOD, kill ОС) может дать **файл нужного размера,
целиком состоящий из нулей**: метаданные (файл существует, размер, выделенные блоки)
журналируются NTFS и переживают краш, а сами данные остаются в page-cache и физически на
диск ещё не легли. Зеркало (`_mirror`), которое пишется тем же мигом теми же байтами, от
этого не спасает — оно теряется вместе с оригиналом.

Пакет закрывает это **двумя слоями защиты**:

1. **Durable-запись основного файла (всегда).** `tmp → writeFile → fsync(данные) →
   rename → fsync(каталога, best-effort)`. fsync данных **до** rename гарантирует, что на
   диске окажется либо старый файл целиком, либо новый целиком — никогда нули.
2. **Отложенный бэкап версий (opt-in, параметр `backup`).** Основной файл уже сохранён, а
   бэкап durable-ложится на диск **через несколько секунд**. Разнесение во времени
   означает, что одно окно сбоя не может задеть и рабочий файл, и бэкап одновременно.

## Установка / импорт

Пакет подключается по правилам PackageLab (см. `_docs/consumers`). Импорт — только из
публичного `index.js`:

```js
import { createSafeFileWriter } from "../../packages/safe-file-writer/index.js";
```

## Быстрый старт

```js
const writer = createSafeFileWriter({ baseDir: "W:/path/to/db" });

// обычная durable-запись без бэкапа
await writer.writeFile("clipboard.jsonl", text);

// durable-запись + отложенный бэкап
await writer.writeFile("ui.json", json, { backup: true });

// при штатном завершении приложения — сбросить отложенные бэкапы на диск
app.on("before-quit", () => writer.close());
```

`writeFile` возвращается сразу после того, как **основной** файл durable-записан. Бэкап
планируется в фоне и не задерживает вызов.

## Параметр `backup`

Управляет вторым слоем — бэкапом. Принимает `true` (взять дефолты) или объект опций
(переопределить дефолты только для этого вызова):

```js
await writer.writeFile("ui.json", json, {
  backup: {
    dir: "_backup",     // куда класть бэкап (по умолчанию — рядом с файлом)
    keepVersions: 3,    // сколько версий хранить
    delayMs: 3000,      // debounce: задержка "тишины" перед записью бэкапа
    maxDelayMs: 15000,  // жёсткий потолок задержки для непрерывно пишущихся файлов
    suffix: ".bak",     // расширение бэкапа
  },
});
```

### Имя и расположение бэкапа

Формат имени **не зависит от расположения**:

```
последняя версия:  <имя-файла>.bak         напр. ui.json.bak
старые версии:     <имя-файла>.bak.<n>      напр. ui.json.bak.1  (n=1 новее n=2)
```

- `backup.dir` **не задан** → бэкап кладётся рядом с основным файлом.
- `backup.dir` **задан** → под этим каталогом сохраняется относительная подпапка
  исходного файла (`_backup/sub/ui.json.bak`), поэтому файлы с одинаковым именем из
  разных папок не затирают друг друга. Само имя файла при этом то же самое.

### Модель версий

- `keepVersions: 1` (по умолчанию) — один `<имя>.bak`, атомарно заменяется durable-записью.
- `keepVersions: N` — новейшая версия `<имя>.bak` плюс `<имя>.bak.1 … <имя>.bak.(N-1)`.

Существующие бэкапы **никогда не перезаписываются на месте**: новая версия пишется через
`tmp → fsync → rename`, старые ротируются, лишние удаляются только после того, как новая
версия уже на диске. Поэтому краш во время бэкапа не портит предыдущую хорошую версию — в
любой момент есть минимум одна целая точка восстановления.

## Механизм отложенного бэкапа

- **Debounce + потолок.** Быстрые повторные записи одного файла коалесцируются: бэкап
  пишется через `delayMs` тишины. Для «горячих» файлов (напр. `ui.json`, который
  переписывается почти на каждый захват буфера) `maxDelayMs` гарантирует, что бэкап всё
  равно делается периодически.
- **Никогда не блокирует приложение.** Планирование — через таймеры (`unref`, чтобы не
  держать процесс живым), запись — async I/O, одновременно не более одной записи бэкапа на
  путь.
- **`flush(rel?)`** — форсировать запись отложенного бэкапа немедленно (без аргумента —
  все ожидающие).
- **`close()`** — сбросить все отложенные бэкапы и остановить таймеры. Вызывать при
  штатном завершении.

Настройки задержки живут в `config.js` (`BACKUP_DEFAULTS`) и переопределяются на инстанс
(`createSafeFileWriter({ backup })`) или на вызов (`writeFile(..., { backup })`).

## Восстановление

```js
const versions = await writer.listBackups("ui.json");
// [{ version: 0, path, size, mtimeMs }, ...]  — новее → старее

await writer.restore("ui.json");                 // из последней версии (.bak)
await writer.restore("ui.json", { version: 1 }); // из предыдущей (.bak.1)
```

## API

`createSafeFileWriter(options)` → writer.

Опции: `baseDir` (обязателен), `durability` (`"fsync"` | `"none"`, по умолчанию
`"fsync"`), `fsyncDir` (bool), `backup` (дефолты бэкапа для инстанса), `onBackupError`
(колбэк ошибок фонового бэкапа).

Методы writer:

| Метод | Назначение |
|---|---|
| `writeFile(rel, data, { backup })` | Durable-запись всего файла; при `backup` — отложенный бэкап. |
| `writeFileAtomic(rel, data, opts)` | Алиас `writeFile` для drop-in совместимости со storage-adapter. |
| `appendLine(rel, line, { backup })` | Durable-дозапись строки; `backup` копирует текущий файл целиком. |
| `readText(rel)` / `readBytes(rel)` | Чтение (`null`, если файла нет). |
| `exists` / `ensureDir` / `remove` / `removeDir` / `list` / `rename` / `resolve` | Обслуживание файлов. |
| `flush(rel?)` | Форсировать отложенный бэкап (все, если без аргумента). |
| `close()` | Сбросить бэкапы и остановить таймеры. |
| `listBackups(rel, backup?)` | Список существующих версий бэкапа. |
| `restore(rel, { version, backup })` | Восстановить основной файл из бэкапа. |

Дополнительно из `index.js` доступны низкоуровневые примитивы `writeFileDurable` и
`appendLineDurable` — для потребителей, которым нужен только fsync-фикс без планировщика.

## Интеграция как storage-adapter

Writer совместим по форме с адаптером хранилища (напр. `node-file-storage` в `notes-db`):
у него есть `writeFileAtomic`, `appendLine`, `readText`, `readBytes`, `exists`,
`ensureDir`, `remove`, `list`, `rename`, `resolve`. Чтобы вся запись стала durable и
получила бэкап, адаптер приложения делегирует в safe-file-writer, а «горячие» снапшоты
(например `ui.json`) пишет с `{ backup: true }`.

## Заметки о платформе

- fsync данных на Windows — это `FlushFileBuffers`; именно этого шага не хватало в кейсе
  «79 нулей».
- fsync каталога актуален для POSIX (durability самого rename). На Windows открыть каталог
  как файл штатно нельзя, поэтому шаг — no-op; durability там обеспечивают fsync данных до
  rename и журнал метаданных NTFS.
- Жёсткий сбой в момент, когда отложенный бэкап ещё не сброшен, теряет только этот
  последний дельта-бэкап: основной файл durable-записан, а предыдущая версия бэкапа цела.
